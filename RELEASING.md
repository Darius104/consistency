# Cutting a desktop release

Desktop only - iOS has no self-update mechanism outside the App Store/
TestFlight, so this only ever applies to the macOS `.dmg`/`.app.tar.gz`
published to [GitHub Releases](https://github.com/Darius104/consistency/releases).

The signing key lives at `~/.tauri/consistency-updater.key` on this Mac -
it was generated once, has no password, and is never committed. Losing it
means no future release can be verified as authentic by apps that already
have the current public key baked in, so there's no way to "reset" it
without breaking updates for everyone already on a signed version.

## Steps

1. Bump the version number in **both** `src-tauri/tauri.conf.json`
   (`"version"`) and `src-tauri/Cargo.toml` (`version = "..."`) - keep them
   in sync.
2. Build with the signing key set, so `createUpdaterArtifacts` (already on
   in `tauri.conf.json`) produces a signed `.app.tar.gz` alongside the
   normal `.dmg`:
   ```sh
   export TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/consistency-updater.key)"
   npm run tauri build
   ```
3. Verify the embedded asset hash matches `dist/assets/` before publishing
   anything (same check as every other build this project does):
   ```sh
   ls dist/assets/
   strings src-tauri/target/release/bundle/macos/Consistency.app/Contents/MacOS/tauri-app | grep -o "index-[A-Za-z0-9_-]*\.\(js\|css\)" | sort -u
   ```
4. The build produces, under `src-tauri/target/release/bundle/`:
   - `dmg/Consistency_<version>_aarch64.dmg` - for fresh manual installs
   - `macos/Consistency.app.tar.gz` + `macos/Consistency.app.tar.gz.sig` -
     for the updater plugin's own in-place updates
5. Write `latest.json` (any editor/heredoc is fine, it doesn't need to be
   generated by a tool) - **the filename must be exactly `latest.json`**,
   since the app's `endpoints` config points at
   `.../releases/latest/download/latest.json`, which always resolves to
   whatever the newest release's asset with that exact name is:
   ```json
   {
     "version": "<new version, no leading v>",
     "notes": "<short human-readable changelog>",
     "pub_date": "<current UTC time, RFC 3339, e.g. 2026-09-19T12:00:00Z>",
     "platforms": {
       "darwin-aarch64": {
         "signature": "<contents of the .sig file>",
         "url": "https://github.com/Darius104/consistency/releases/download/v<new version>/Consistency.app.tar.gz"
       }
     }
   }
   ```
6. Create the GitHub release, uploading all three files together:
   ```sh
   gh release create v<new version> \
     "src-tauri/target/release/bundle/dmg/Consistency_<new version>_aarch64.dmg" \
     "src-tauri/target/release/bundle/macos/Consistency.app.tar.gz" \
     latest.json \
     --title "Consistency v<new version>" \
     --notes "<release notes>"
   ```
7. Also upload a **fixed-name copy** of the dmg, so the download page's link
   never has to change between releases (GitHub's `.../releases/latest/
   download/<name>` always resolves to whatever the newest release's asset
   with that exact name is - same trick `latest.json` already relies on):
   ```sh
   cp "src-tauri/target/release/bundle/dmg/Consistency_<new version>_aarch64.dmg" /tmp/Consistency-aarch64.dmg
   gh release upload v<new version> /tmp/Consistency-aarch64.dmg
   rm /tmp/Consistency-aarch64.dmg
   ```
   The download page (`docs/index.html`, published via GitHub Pages) links
   straight to `https://github.com/Darius104/consistency/releases/latest/download/Consistency-aarch64.dmg` -
   nothing on that page needs updating when a new version ships.
8. Deploy locally too (`rm -rf /Applications/Consistency.app && cp -R ... /Applications/`)
   so this Mac's own install stays current, same as every other build this
   session does.

Only an Apple Silicon (`aarch64`) build exists right now - there's no Intel
(`x86_64`) artifact, so `latest.json` only has one entry under `platforms`.
